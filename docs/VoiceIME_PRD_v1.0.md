# 1  产品背景
## 1.1  项目起源
VoiceIME 是一个运行在 Windows 个人电脑上的本地语音输入工具，专为日常开发、写作与沟通场景设计。项目由开发者本人主导，核心诉求是「随时按键说话，松开即上屏」。
市面上主流语音输入法（如讯飞、搜狗）存在以下痛点：
- 依赖云端服务，存在隐私泄露风险
- 中英文混输识别率不稳定
- 无法感知当前应用上下文，输出千篇一律
- 专有名词（项目名、API 名称、技术术语）识别错误率高
- 无法与 LLM 深度集成做后处理润色

## 1.2  核心价值主张

| 维度 | 市售输入法 | VoiceIME |
| --- | --- | --- |
| 数据隐私 | 云端处理，存在泄露风险 | 100% 本地推理，零网络请求 |
| 识别精度 | 通用模型，术语识别差 | 热词词库，可定制纠错 |
| 上下文感知 | 无 | 读取当前窗口，动态切规则 |
| LLM 润色 | 无 | 一键润色，口语转书面语 |
| 硬件利用率 | 不感知 NPU/核显 | 支持 Vulkan 充分利用 780M |

一句话总结：**本地推理 + 热词定制 + LLM 润色 + 上下文感知 = 开发者专属的隐私安全语音输入法。**

## 1.3  非目标（Out of Scope）
- 不开发 TSF 原生 Windows 输入法框架集成（工程复杂度过高，收益有限）
- 不支持多用户 / 多账户场景，纯个人自用工具
- 不做移动端原生 App（远程调用服务端即可）
- 不做语音合成（TTS），仅做语音识别（ASR）

## 2.2  核心使用场景
### 场景 A：代码开发中快速写注释
场景描述  用户在 VSCode 中编写代码，需要快速添加函数注释，不想打断编码节奏切换输入法。
触发：按住 Caps Lock → 说「这个函数负责解析 NL2SQL 的 agent 输出，返回 SQL 字符串和置信度分数」→ 松开 → 识别结果自动格式化为代码注释风格上屏。

### 场景 B：撰写工作文档
场景描述  用户在 Notion 或 Word 中撰写 PRD，口头组织好一段话后希望直接转为正式书面语。
触发：按住 Caps Lock → 说「这个功能就是让用户可以把说的话转成文字，然后放到当前光标位置」→ 松开 → 悬浮条显示结果 → 点击「LLM 润色」→ 自动改为「该功能支持将用户语音实时转录为文字，并插入至当前光标所在位置」→ 上屏。

### 场景 C：即时通讯快速回复
场景描述  用户在微信 / 企业微信 / Slack 中需要快速回复消息，直接语音说中文即可上屏。
触发：切换到聊天窗口 → 按住热键 → 说「好的，下周一上午十点我有空，可以开会」→ 松开 → 直接上屏，无需确认。

# 3  核心功能规格
功能按优先级分为三级：P0（MVP 必做）、P1（推荐迭代）、P2（进阶扩展）。


## 3.1  全局热键录音触发  [P0]
### 3.1.1  功能描述
在任意前台窗口（VSCode、微信、浏览器、记事本等），按下并保持预设热键即开始录音，松开热键触发语音识别，识别完成后展示悬浮结果条。

### 3.1.2  功能规格

| 规格项 | 规格值 |
| --- | --- |
| 默认热键 | Caps Lock（可在设置中修改） |
| 录音触发方式 | keydown 事件触发开始，keyup 事件触发停止 |
| 最短录音时长 | 200ms（低于此值不触发识别，视为误触） |
| 最长录音时长 | 60 秒（超时自动停止并触发识别） |
| 录音采样率 | 16000 Hz（Whisper 模型标准输入格式） |
| 录音声道数 | 单声道（Mono） |
| 热键冲突检测 | 若热键已被其他程序占用，启动时弹出警告并提示更换 |
| 全局钩子方式 | Windows Low-Level Keyboard Hook（WH_KEYBOARD_LL） |
| Caps Lock 行为 | 拦截期间 Caps Lock 灯不切换，大小写状态冻结；录音结束后恢复原有大小写状态 |
| 悬浮条定位 | 主显示器顶部中央；多显示器时跟随当前焦点窗口所在显示器 |

### 3.1.3  交互流程说明
- 用户按下热键（keydown）→ 系统注册全局键盘钩子，开始从麦克风采集 PCM 音频流，写入临时缓冲区。
- 悬浮录音条从屏幕顶部中央滑入，显示红色录音指示点与实时波形动画，右侧显示已录制时长（精确到 0.1 秒）。
- 用户持续说话。VAD（语音活动检测）模块实时监测音频能量，自动标记有效语音段落起止时间。
- 用户松开热键（keyup）→ 停止录音 → VAD 裁剪首尾静音 → 音频送入推理引擎。
- 推理进行中，悬浮条切换为「识别中...」状态，波形动画替换为进度指示器。
- 识别完成 → 悬浮条展示识别文本、语言标签、耗时与当前聚焦窗口名 → 用户可确认上屏、润色或重录。

异常处理  若录音期间麦克风设备断开，立即停止录音并在悬浮条显示「麦克风连接中断，请检查设备」错误提示。

## 3.3  语音识别引擎（ASR）  [P0]
### 3.3.1  功能描述
使用开源 Whisper 模型（faster-whisper 或 whisper.cpp）在本地进行语音转文字推理，支持中英文及中英混说的自动识别，无需手动切换语言。

### 3.3.2  模型选型对比

| 方案 | 推理库 | 加速后端 | 中文准确率 | 推荐度 |
| --- | --- | --- | --- | --- |
| 方案 A（推荐） | faster-whisper | CPU (AVX2) | ★★★★★ | ✓ MVP 首选 |
| 方案 B（进阶） | whisper.cpp | Vulkan (780M) | ★★★★★ | ✓ Phase 2 评估 |
| 方案 C（备选） | SenseVoice | CPU (ONNXRuntime) | ★★★★☆ | 中英混说测试后决定 |

### 3.3.3  推理配置规格

| 配置项 | 默认值 | 说明 |
| --- | --- | --- |
| 模型版本 | large-v3-turbo | 准确率与速度最佳平衡点 |
| 量化精度 | int8 | 减少内存占用，速度提升约 2x，精度损失可忽略 |
| 语言设定 | auto | 自动检测中文 / 英文 / 中英混说 |
| VAD 过滤 | 开启 | 内置 Silero VAD，vad_filter=True |
| VAD 阈值 | 0.5 | 能量阈值，可在设置中微调；中文场景建议 0.3–0.5 |
| Beam Size | 5 | 解码 beam 数，越大越准但越慢 |
| 模型常驻内存 | 是 | 启动时加载，使用 VirtualLock 锁定物理内存防换出 |
| 最大推理超时 | 30 秒 | 超时返回空串并提示错误 |

### 3.3.4  内存保活机制（防止模型被 Windows 换出）
Windows 的内存分页机制会将长期无 I/O 的进程内存压缩至虚拟内存（Pagefile），导致首次唤醒时从 SSD 重新加载模型，产生数秒卡顿。

解决方案：
- Python 层使用 ctypes 调用 Win32 API VirtualLock 锁定模型权重所在的内存页，阻止系统换出。
- 每隔 30 秒执行一次「心跳访问」，读取模型的元数据（不做实际推理），维持进程活跃状态。
- 在设置界面提供「内存锁定」开关，默认开启；可关闭以在低内存场景让出资源。

## 3.4  文本上屏（输出）  [P0]
### 3.4.1  功能描述
将识别完成的文本注入当前聚焦的应用程序，支持剪贴板注入（主路径）和 UIAutomation 注入（辅助路径）两种方式，并保证注入后剪贴板内容恢复原状。

### 3.4.2  上屏策略（分层 Fallback）

| 优先级 | 方式 | 适用场景 | 失败条件 |
| --- | --- | --- | --- |
| 1（首选） | 剪贴板 + Ctrl+V 模拟 | 99% 通用场景 | 剪贴板被其他进程锁定（极少见） |
| 2（辅助） | UIAutomation Value Pattern | 标准 Win32 / WPF 文本框 | 目标控件不支持 UIA Value Pattern（Chrome/Electron/微信等大多不支持） |
| 3（兜底） | pyautogui 逐字符输入 | 剪贴板不可用时 | 速度慢，作为最后兜底 |

说明  UIAutomation 虽然技术更"干净"，但实际可用范围远窄于剪贴板方案，因此将剪贴板列为主路径。

### 3.4.3  剪贴板保护流程
- 识别文本就绪，准备上屏。
- 备份当前剪贴板内容（文本 / 图片 / 文件路径均支持）至程序内存。
- 将识别文本写入剪贴板。
- 向聚焦窗口发送 Ctrl+V 按键事件。
- 等待 50ms（确保目标应用完成粘贴操作）。
- 将原剪贴板内容恢复至剪贴板。
- 关闭悬浮结果条，完成本次输入。

注意  如果用户在 50ms 内手动操作了剪贴板（极端情况），恢复操作会覆盖用户最新复制的内容。此风险极低，暂不处理；如有需要可在设置中关闭「自动恢复剪贴板」功能。

## 3.5  文本后处理层  [P1]
### 3.5.1  功能描述

# 4  非功能性需求
## 4.1  性能需求

| 指标 | 目标值 | 测量方式 |
| --- | --- | --- |
| 首次模型加载时间 | ≤ 8 秒（SSD 冷启动） | 程序启动到托盘图标变绿的时间 |
| 二次唤醒延迟 | < 100ms（内存锁定后） | 热键按下到录音条出现的时间 |
| 5 秒音频推理耗时（CPU） | ≤ 2.5 秒（int8） | 松开热键到结果显示的时间 |
| 5 秒音频推理耗时（Vulkan） | ≤ 1.5 秒（目标值） | Phase 2 评估后确定 |
| 内存占用（模型加载后） | ≤ 4 GB | Windows 任务管理器工作集 |
| CPU 占用（待机状态） | < 1% | 托盘常驻时的 CPU 使用率 |
| 剪贴板恢复延迟 | ≤ 100ms | 上屏后到原剪贴板内容恢复的时间 |
| 悬浮条显示延迟 | < 50ms | 热键按下到悬浮条滑入完成 |

## 4.2  可靠性需求
- 进程异常崩溃后，全局热键钩子必须自动注销（避免 Caps Lock 永久失效）。
  - 实现方式：`atexit` 注册清理 + `try/finally` 双保险；对于 kill -9 / 任务管理器强杀，依赖 Windows 在进程终止时自动卸载 WH_KEYBOARD_LL DLL。
- 剪贴板备份恢复失败时，记录错误日志并提示用户，不静默丢失数据。
- 模型文件损坏或缺失时，启动时检测并提示下载，程序以「降级模式」（无 ASR，仅托盘图标）运行。
  - 降级模式下：托盘图标红色，右键菜单「热键录音」项禁用，「设置」和「退出」可用。
- config.json 损坏时（JSON 解析失败），自动重命名为 `config.json.bak`，创建默认配置，悬浮提示「配置文件已恢复为默认值」。
- hotwords.json 损坏时，自动重命名为 `hotwords.json.bak`，创建空词库，悬浮提示「热词词库已重置」。
- history.sqlite 损坏时（PRAGMA integrity_check 失败），自动重命名为 `history.sqlite.bak`，创建新数据库，悬浮提示「历史记录已重置」。
- 禁止多实例启动：使用 Win32 命名互斥体（`Global\VoiceIME_SingleInstance`），第二个实例启动时检测到互斥体已存在，激活已运行实例的托盘图标后退出。
- Windows 休眠/恢复后：VirtualLock 仍有效（物理内存页在休眠恢复后由 OS 还原）；音频设备可能需要重新初始化，在下次热键触发时检测设备可用性，不可用时自动重新打开录音流。

## 4.3  安全与隐私需求
- 所有语音数据 100% 本地处理，不发送至任何第三方服务器（LLM 润色除外，用户知情并主动触发）。
- API Key 使用 Windows Credential Manager 加密存储，不写入任何明文配置文件。
- 历史记录数据库（SQLite）仅存储在用户本地目录，不同步至云端。

## 4.4  兼容性需求
- 操作系统：Windows 10 (22H2) 及以上；Windows 11 全版本。
- 运行时：Python 3.11+，首次安装自动检测并提示。
- 主要兼容目标应用：VSCode、Notion Desktop、微信 PC 版、Chrome、Microsoft Office 全家桶、Windows 记事本。

## 6.3  运行时架构（线程与事件循环）

VoiceIME 涉及 5 个并发事件源，必须明确定义线程归属与通信方式。

### 6.3.1  线程模型

```
┌───────────────────────────────────────────────────────────┐
│  主线程（PyQt6 事件循环 / QApplication）                   │
│   · PyQt6 主循环                                          │
│   · 悬浮条 / 设置窗口 / 热词词库 / 历史记录               │
│   · 后处理管道编排                                        │
│   · 剪贴板上屏                                            │
├───────────────────────────────────────────────────────────┤
│  托盘线程（pystray 独立线程）                              │
│   · 系统托盘图标 + 右键菜单                               │
│   · 通过队列向主线程发送指令（录音/暂停/退出）             │
├───────────────────────────────────────────────────────────┤
│  热键监听线程（pynput Listener）                           │
│   · 全局键盘钩子                                          │
│   · keydown/keyup 事件通过队列通知主线程                   │
├───────────────────────────────────────────────────────────┤
│  音频线程（sounddevice 回调）                              │
│   · PCM 采集回调，写入 ring buffer                        │
│   · 禁止在回调中做任何阻塞操作                            │
├───────────────────────────────────────────────────────────┤
│  推理线程（faster-whisper 调用）                           │
│   · CPU 密集型阻塞，必须在独立线程                        │
│   · 推理结果通过队列回传主线程                            │
└───────────────────────────────────────────────────────────┘

线程间通信：queue.Queue（线程安全 FIFO）
主线程消费队列时机：QTimer 定时轮询（50ms 间隔）
```

### 6.3.2  UI 框架决策

| 决策项 | 方案 | 理由 |
| --- | --- | --- |
| 主 UI 框架 | PyQt6 | 现代外观，支持丰富控件，波形动画性能好 |
| 托盘图标 | pystray（独立线程） | 轻量，不依赖 PyQt6 事件循环；PyQt6 QSystemTrayIcon 备选 |
| 悬浮条 | PyQt6 QWidget (Qt.ToolTip | Qt.WindowStaysOnTopHint) | TopMost + 不抢焦点 |
| 事件循环关系 | PyQt6 为主循环，pystray/pynput/sounddevice 跑独立线程 | 避免 Qt 事件循环与第三方库冲突 |

### 6.3.3  进程模型

单进程架构。不做多进程拆分，理由：
- 32GB 内存充裕，无需通过多进程隔离内存
- 多进程增加 IPC 复杂度，收益不足以覆盖成本
- 通过线程隔离保证 UI 响应性即可
